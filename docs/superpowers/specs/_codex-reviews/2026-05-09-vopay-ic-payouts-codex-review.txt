    apps/api/src/portal-messages/portal-messages.controller.ts:27, tailfire/apps/

    incomplete. The auth path is sound: PortalAuthGuard always enforces portal JWT
    auth in tailfire/apps/api/src/auth/guards/portal-auth.guard.ts:14, the
    strategy requires a portal user plus contact_id and agency_id in tailfire/
    apps/api/src/auth/strategies/portal-jwt.strategy.ts:84, and the controller
    resolves the contact from contacts.portal_user_id = token.sub in tailfire/

    That is a data-integrity hole.
  - Medium markAsRead is semantically wrong for trip-scoped views and long
    threads. GET /portal/my-messages marks messages read before fetching in
    tailfire/apps/api/src/portal-messages/portal-messages.controller.ts:33,
    markAsRead() updates all unread agent messages for the contact with no tripId

  Direct answers

  1. GET /portal/my-messages is properly consumer-scoped. The route does not trust
     a client-supplied contact id; it resolves the contact from the authenticated
     portal user and filters by that contact.
  2. POST /portal/my-messages does prevent senderType='agent' injection. The DTO
     only accepts body and optional tripId, and the service hardcodes senderType:
     'consumer'.
  3. tripId on GET does not do a formal trip-membership check, but it also does
     not leak other consumers’ messages because the query is contactId AND tripId.
     The real gap is POST, where tripId is not ownership-validated at all.
  4. GET /portal/my-payments is broadly scoped to the consumer’s trips only by
     traveler/primary-contact association in tailfire/apps/api/src/portal/
     portal.service.ts:627. The logic is sound enough, but it is looser than
     getTripsForPortalUser() because it does not also agency-scope. The bigger
     problem is the broken paymentSummary shape.
  5. The specific race you described is not accurate. A message arriving after
     markAsRead() will remain unread. The actual correctness issue is that opening
     the inbox marks unrelated or not-yet-returned agent messages as read.
  6. getMessagesForContact() has no N+1 issue. Polling cost is linear with active
     open inboxes, and each poll currently re-fetches up to 100 rows.
  7. getUnreadCount() should use count(*), not row materialization plus .length.
     At scale, this becomes unnecessary load.
  8. sendFromAgent() is not exposed through any admin endpoint or UI that I found
     on main. That is a real hole.
  9. There is no realtime fallback beyond polling. No WebSockets, no SSE, no
     notifications, and no wired unread badge surfaced in the client.

  Recommended changes

  - Fix payments first. Either map paymentSummary into a portal DTO on the
    backend, or change the client to consume the real stored shape. Do not pass
    raw trip-order snapshot JSON straight through.
  - Add trip access validation on both message read and write paths. On GET,
    validate tripId as UUID and confirm the contact belongs to the trip. On POST,
    reject trip IDs the consumer does not own.
  - Change read semantics: fetch first, then mark only the returned unread agent
    message ids as read, ideally scoped by tripId and paired with pagination.
  - Expose an agent reply path before calling this complete. The schema and
    service assume admin-originated writes, but the merged code does not deliver
    them.
  - Replace unread .select().length with count(*), and add a better unread index
    such as a partial index on unread agent messages by contact_id.
  - Add an error state to the portal messages page.

  ## Context
  Tailfire is a multi-tenant travel-agency platform (NestJS API + Next.js admin). The existing
  commission module (apps/api/src/financials/commission/) tracks supplier-received checks,
  agent payouts, and settlements with two-stage commission splits. Today, the IC payout flow is
  record-only — admins cut real e-Transfers/wires manually outside Tailfire.

  ## Goal of this design
  Build a CRA-conformant Independent Contractor (IC) self-serve commission disbursement system.
  Phase 1 ships full mechanics with MANUAL money movement (admin sends Interac e-Transfer or
  Wise wire by hand and records proof). Phase 2 swaps in VoPay or DreamPay behind a
  `PayoutProvider` interface — no schema or workflow change.

  ## Locked decisions (from user brainstorming)
  - Single-tenant v1 (Phoenix Voyages); Doppler-stored config
  - Self-invoicing PDF generated by Tailfire (CRA recipient-created tax invoice pattern;
  written authorization e-signed once per IC, re-prompt on agreement version bump)
  - Probationary trust: ICs get an `auto_disburse` flag (admin-set only, no auto-graduation)
  - Aggregate invoices — IC selects multiple eligible commissions per claim
  - Mixed-currency claim splits into one invoice per currency
  - Auto GST/HST gross-up by IC's province if registered (per-IC `gstHstNumber` + province →
  tax rate)
  - Full T4A: PDF + CRA XML XFile generation (Box 048 Fees for Services)
  - Currency for payout = original commission's currency (CAD/USD; multi-account per IC, one
  default per currency)
  - Failure handling: unsettle claimed items, return to "eligible", notify IC + admin
  - Canadian residents only in v1 (US/intl ICs are future add-ons)
  - No cheques, ever
  - No settlement holdback beyond existing trip-status filter (`travelling`/`travelled` AND
  supplier-check accepted)
  - Adjustments: all pending IC-targeted `commission_adjustments` auto-roll into next claim
  - USD on T4A: snapshot Bank of Canada daily rate on payout-completion date;
  cadEquivalentCents stored on disbursement

  ## Architecture
  - New NestJS module `IcPayoutModule` with services: IcPayoutAccounts, IcInvoice,
  IcInvoicePdf, Disbursement, TaxYear, T4ASlip, FxRate
  - `PayoutProvider` strategy interface with `ManualProvider` (v1 only). v2 adds VoPay or
  DreamPay.
  - Existing `commission_checks` (paid type) + `commission_item_settlements` are KEPT and
  reused — when an invoice is approved, system creates legacy paid-check + settlements
  internally so legacy reports/payAgents still work.
  - Admin and IC interact only with the new entities.

  ## New tables (Drizzle/Postgres, all carry agencyId + audit FKs)
  1. `ic_payout_accounts` — multi-account per IC, keyed by currency. Fields: userId, label,

  2. `ic_payout_authorizations` — one per IC self-invoice authorization acceptance:

  4. `ic_invoice_lines` — lineType (commission|adjustment), checkItemId or adjustmentId FK,

  5. `ic_disbursements` — 1:1 with invoice. Fields: invoiceId, payoutAccountId (snapshot),

  Findings

  - Critical The T4A mapping is likely wrong. CRA’s current T4A materials distinguish self-
    employed commissions from fees for services, and Box 048 explicitly excludes GST/HST/PST.
    Your ic_t4a_slips.Box048Cents = sum(disbursements.cadEquivalentCents) would overreport
    whenever the payout includes tax. If these are IC commission payouts, Box 020 may be the
    closer fit than Box 048. At minimum, you need separate fields for reportableBaseCadCents,
    taxCadCents, and disbursedCadCents. External: CRA T4A slip and XML spec. Internal context:
    current commission payouts are explicitly commissions, not generic AP invoices. tailfire/
    apps/api/src/financials/commission/commission.service.ts:608
  - Critical The GST/HST province logic in the design is not consistent with CRA’s general
    place-of-supply rule for services. CRA’s default rule is based on the recipient’s Canadian
    address, often the contracting address, not the contractor’s province of residence. In this
    model Phoenix is usually the recipient of the IC’s service, so a blanket “IC province
    determines rate” rule is not safe. You need a place-of-supply decision model plus effective-
    dated rate tables. Internal config today has no payer payroll/tax account metadata beyond
    generic business info. tailfire/packages/database/src/schema/financials.schema.ts:280
  - Critical Creating the legacy paid check and settlements only on invoice approval is too late
    if invoice submission is meant to reserve commissions. The current eligibility engine
    excludes payable items only after commission_item_settlements exists, and payAgents()
    atomically claims both settlements and pending adjustments in one transaction. If you wait
    until approval, the same commission can remain eligible and be claimed again. You need
    either:

        adjustments, or
      - legacy settlement artifacts created at claim submission, then reversed on rejection/

  Direct Answers

  1. Reuse vs replace: reuse is acceptable only as an internal ledger/eligibility artifact with
     one write path. Do not leave payAgents and claims/me live in parallel.
  2. Provider seam: keep PayoutProvider, but run sends, retries, and status transitions through
     jobs plus webhook handlers.
  3. Self-invoice CRA pattern: version, timestamp, IP, and signature evidence are directionally
     right, but add agreement text hash, rendered agreement artifact, and payer/recipient tax-
     registration attestations. I would still require tax/legal review because I did not find a
     CRA page that explicitly blesses your exact RCTI flow.
  4. GST/HST math: do not key tax rate off the IC province alone. Determine place of supply from
     the CRA service rules, usually the recipient/contracting address unless a specific
     exception applies.
  5. FX for T4A: daily Bank of Canada rate on payout completion date is defensible and more
     auditable than monthly average. Monthly average is acceptable only if you choose it
     consistently.
  6. Multi-currency split: clean operationally, but only after you make eligibility and
     adjustments currency-aware.
  7. Encryption boundary: current app-layer encryption is a baseline, not a best-in-class SIN
     control. KMS is not explicitly required by PIPEDA, but minimization, key rotation/
     versioning, and strict access control are needed.
  8. Idempotency: yes, keep idempotencyKey in v1 and make it unique.
  9. Admin approval ceiling: yes, add a hard cap even for auto_disburse ICs.
  10. Year-end T4A locking/amendments: the direction is right. Preserve original slips, create
     explicit amended filings, and use CRA amendment semantics rather than mutating prior-year
     records.

  Recommended revisions

  - Add ic_profiles / ic_tax_profiles as the canonical contractor record.
  - Add currency to commission_adjustments, and make claim selection grouped by received-check
    currency.
  - Add reservation semantics before approval.
  - Change T4A design to store reportable base separately from tax and total payout.
  - Replace ...Url columns with storage-path columns plus signed-read generation.
  - Add payer payroll/tax filing config at the agency level.
  - Add ic_disbursement_attempts and a queue-backed payout orchestrator.
  - Add explicit rejected invoice status and a clearer invoice/disbursement state machine.
